# Security and privacy

## Principles
1. **Least data leaves the extension.** Web pages receive only the values for one run. Executions, audit and logs never contain field values.
2. **Sensitive data is never in plain text at rest or in the cloud.**
3. **User code never gets extension privileges.**
4. **Humans stay in control.** No CAPTCHA/MFA bypass, no automatic submission of official forms, confirmation before submit, pay or delete actions.
5. **The cloud enforces authorization.** Firestore rules mirror the RBAC model, and they are tested on the emulator.

## Encryption
| What | How |
|---|---|
| Sensitive dataset columns, AI API keys | AES-256-GCM, random 96-bit IV, **non-extractable** device key generated by WebCrypto and stored in IndexedDB |
| Vault secrets | AES-256-GCM with the master key from **PBKDF2-SHA256 (310,000 iterations)** of the user's passphrase plus a 16-byte salt. The record id is bound as AAD. |
| Unlock session | The derived key is held only in `chrome.storage.session` (memory, trusted contexts) and expires after the auto-lock time |
| Cloud copies of sensitive datasets | Re-encrypted with the master key (`encm:v1:`), only if the user enables it and the organization allows it |
| Cloud backups | The whole bundle is encrypted with the master key before upload |
| File backups | Encrypted with a backup passphrase (PBKDF2 + AES-GCM). Without a passphrase, sensitive values are omitted. |

The passphrase is never stored. The vault configuration (salt and an encrypted verifier) syncs, so the same passphrase works on every device.

## JavaScript automation sandbox
* Scripts are parsed with **acorn**. Syntax errors, extension APIs, `eval`/`Function`, dynamic `import()` and reserved names are rejected.
  Network and storage use produce warnings.
* Every loop body gets a guard (iteration limit and wall-clock deadline). Every statement records its line for error reports.
* Execution uses the **sval** interpreter injected into the page's **main world**, so there is no `eval` and it works under strict CSP.
  That world has no `chrome.*` extension APIs.
* sval copies the real global object into its sandbox. K-Flow **strips the sandbox global to standard ECMAScript built-ins**,
  so `fetch`, `localStorage`, `document.cookie` through the global, and `chrome` are unavailable, and the hidden reference to the real global is removed.
  Unit tests verify this.
* Dashboard dry runs execute inside the MV3 **sandbox page** (opaque origin, no extension APIs). The extension pages never run user code.
* Scripts receive variables and the active record, but **never vault secrets**. `kf.click` refuses submit, pay and delete buttons.
* Residual risk: a script runs with the same power as the page's own JavaScript. Through prototype chains (`({}).constructor.constructor`)
  it can reach the page's global object on pages whose CSP allows `eval`. It cannot reach the extension.
  Only run scripts you trust, and organizations can disable scripts by policy.

## Message passing
The background ignores messages whose `sender.id` is not K-Flow. Content scripts can act only on their own tab and
cannot list tabs, scan other tabs or render arbitrary templates. Overlay frames use one-time nonces. Window messages are checked
against the exact frame window and origin. Page scripts cannot message the extension (no `externally_connectable`).

## Page safety
* CAPTCHA, reCAPTCHA, hCaptcha and Turnstile fields and OTP/2FA fields are detected and **never filled or recorded**.
* Submit-like actions (submit, pay, delete, transfer, confirm, save & next…) require approval in an extension-owned dialog
  that the page cannot click. On **official domains** every action button requires approval.
* Password fields are filled only from the vault. Recorded password steps are left empty and flagged.
* Domain allowlist, per-site disable, and an organization domain policy.

## Firestore rules (summary)
* Personal data: `users/{uid}/…` is readable and writable only by that user. Backups must be vault-encrypted.
* Organizations:
  * Membership comes from `members`. Ownership is `ownerUid`, not a role string.
  * Actions are checked against `perm[role]`, with per-user `deny` taking precedence and `allow` as an exception list.
  * Admins cannot touch the owner or transfer ownership.
  * Invitees can only add themselves with the invited role.
  * Audit, activity and versions are append-only.
  * Members cannot un-revoke their own devices.
* Tested by `tests/rules/rules.test.mjs`. The suite found and fixed two real holes: tombstone edits were being denied, and the generic
  delete rule allowed deleting audit entries.

## Audit
Local audit log entries cover create, edit, delete, share, import, execute, vault unlock failures, reveals and backups.
Organization audit entries cover membership, permissions, policies, devices and sharing.

## Reporting a vulnerability
Open a private security advisory on the repository.
